## 1. OUR SECURITY COMMITMENT & ARCHITECTURE OVERVIEW

At Classgrid Technologies ("**Company**", "**Classgrid**", "**We**", "**Us**", or "**Our**"), security is embedded into the core architecture of Our public artificial intelligence platform ([https://chat.classgrid.in](https://chat.classgrid.in)). Because Classgrid runs autonomous AI engineering agents, ephemeral Linux development sandboxes, real-time multi-user collaborative Grids, and voice telephony gateways, Our security posture is built upon a strict **Zero-Trust** and **Defense-in-Depth** model.

> **Scope Clarification:** This Security Policy governs the public-facing AI developer platform, APIs, sandboxes, and cloud infrastructure. All legacy institutional ERP systems have been decommissioned. This document outlines the technical and organizational safeguards actively enforced across Our modern distributed cloud environment.

Every layer of Our infrastructure—from client-side device authentication to containerized cloud sandboxes, model inference gateways, and edge telemetry—is designed to isolate workloads, protect developer IP, and mitigate automated attacks.

## 2. AUTHENTICATION & SESSION SECURITY

### 2.1 Passwordless Authentication & Federated Identity
To eliminate credential stuffing and password reuse attacks, Classgrid enforces modern federated authentication:
- **Federated OAuth 2.0 / OIDC:** Secure sign-in through verified identity providers (Google OAuth and GitHub OAuth).
- **Cryptographic Email OTP:** Passwordless magic links and time-limited, single-use One-Time Passwords (OTPs) hashed using SHA-256 before database storage.
- **Strict Anti-Timing Attack Verification:** All session tokens, passwordless verification secrets, and API keys are validated using constant-time cryptographic algorithms (`crypto.timingSafeEqual`) to prevent side-channel timing attacks that infer secret lengths.

### 2.2 Client-Side Device Fingerprinting & Anti-Abuse
Our client applications generate non-reversible hardware environment fingerprints to protect account integrity and block botnets:
- **Hardware Canvas & WebGL Hash:** Mathematical hashes computed from client GPU rendering output and color bit depth.
- **Session Anomaly Detection:** Real-time correlation of device signatures with IP geolocations, blocking hijacked session tokens attempting cross-region access without re-authentication.

### 2.3 Session Token Architecture
- **HttpOnly & Secure Cookies:** Web sessions are secured with cryptographically signed JSON Web Tokens (JWTs) marked `HttpOnly`, `Secure`, and `SameSite=Lax` or `Strict` to prevent Cross-Site Scripting (XSS) extraction.
- **Bearer Token Security:** API bearer tokens are strictly forbidden in URL query parameters and must be transmitted in the `Authorization: Bearer <token>` header.

## 3. PROJECT MODE & CLOUD DEVELOPMENT SANDBOX SECURITY

### 3.1 Ephemeral Container Isolation
Project Mode provides developers with dynamic Linux cloud development environments. Security controls include:
- **Isolated Linux Sandboxes:** Workspaces run inside isolated virtual containers or VMs managed via NodeSSH over private VPC networks. Sandboxes have zero access to the underlying hypervisor or adjacent tenant environments.
- **Ephemeral Storage Lifecycle:** Cloud containers are provisioned on demand. When a development session ends or times out, the container is safely terminated, and the file system is zeroed out.
- **Network Egress Safeguards:** Outbound network connections from sandboxes are monitored and rate-limited. Cloud sandboxes cannot be used to scan internal AWS/cloud metadata services (`169.254.169.254`), execute DDoS attacks, or interact with prohibited botnet command-and-control infrastructure.

### 3.2 2MB File Cap (`MAX_FILE_BYTES = 2MB`)
Individual file uploads into Project Mode sandboxes are subject to a strict 2-Megabyte limit (`MAX_FILE_BYTES = 2 * 1024 * 1024`). This rule prevents:
- Denial-of-Service attacks attempting to exhaust container disk space or memory;
- Decompression bombs ("zip bombs") engineered to crash containerized file system daemons;
- Accidental ingestion of massive uncompiled binary blobs into AI model prompt contexts.

### 3.3 Dynamic GitHub App Installation Tokens
When connecting private repositories:
- Classgrid generates short-lived, narrowly scoped GitHub App installation tokens (`repoAppToken`).
- Tokens expire automatically after 60 minutes and carry permissions restricted strictly to the user-selected repository.
- Automated commits generated by the platform include verified co-authorship metadata (`Co-authored-by: Classgrid AI <noreply@classgrid.in>`), preserving audit transparency in Your git history.

## 4. AUTONOMOUS AI AGENT SAFEGUARDS

### 4.1 Bounded Execution Windows (`MAX_WORK_MS = 48 Hours`)
Autonomous agents execute multi-step engineering directives. To prevent runaway background processes, orphaned cloud jobs, and infinite billing loops:
- Every background agent task is governed by a hard-coded execution ceiling of **48 hours (`MAX_WORK_MS`)**.
- The agent task daemon automatically terminates and archives any task exceeding this threshold.

### 4.2 Automated Circuit Breaker (`NO_PROGRESS_LIMIT = 5`)
To protect User credit balances from repetitive execution failures:
- The system monitors consecutive tool execution outcomes.
- If an agent incurs **five (5) consecutive tool failures** (e.g., repeating syntax errors, failed HTTP requests, or unresolvable compilation flags without state improvement), the circuit breaker trips.
- The task is immediately transitioned to a paused state (`failed_circuit_breaker`), firing diagnostic alerts and preventing unnecessary credit burn.

### 4.3 Secure Tool Invocation
- Agents invoke tools within sandboxed runtime environments.
- System commands, shell executions, and file operations are logged in real-time task audit logs (`models/TaskLog.js`).
- Agents are technically restricted from accessing system-level operating system files or environment configuration variables outside the provisioned workspace directory.

### 4.4 Agent Email Safeguards (`agent-mail.service.js`)
- Outbound emails initiated by autonomous agents require prior User configuration.
- Outbound relays enforce strict rate limiting, SPF, DKIM, and DMARC alignments to prevent spoofing or unauthorized relay usage.

## 5. REAL-TIME COLLABORATIVE GRIDS SECURITY

### 5.1 Multi-User Room Architecture (`GRID_MAX_PEOPLE = 4`)
Grids enable real-time collaboration between developers and AI agents. Security controls include:
- **Hard-Capped Room Membership:** Rooms are restricted to a maximum of **four (4) concurrent users** to maintain low-latency WebSocket synchronization and eliminate room-flooding attacks.
- **Cryptographic Invite Tokens:** Grids use 12-byte cryptographically secure, random base64url tokens. Tokens are non-sequential and resistant to brute-force discovery.
- **Email Masking Privacy (`hideEmail`):** The Platform provides a privacy toggle allowing collaborators to mask their personal email address from room peers, preventing PII harvesting in public or team-shared Grids.

### 5.2 WebSocket Transport Security
- All real-time communication is encrypted in transit using **WSS (WebSocket Secure)** over TLS 1.3.
- WebSocket handshakes validate session JWTs before granting access to Redis pub/sub room channels.
- Connection throttling prevents socket exhaustion attacks.

## 6. WHATSAPP AI VOICE TELEPHONY SECURITY

### 6.1 End-to-End Voice Transport
- Voice telephony is integrated using the official Meta WhatsApp Calling Cloud API.
- Audio packets are streamed over **WebRTC** utilizing the **48 kHz Opus codec**, ensuring carrier-grade encryption and low latency.
- Telephone numbers are validated and mapped 1-to-1 to authenticated Classgrid accounts via signed Meta webhook payloads.

### 6.2 Transient Audio Processing & Zero Long-Term Storage
- Incoming audio streams are ingested in memory and immediately passed through speech-to-text (Whisper STT).
- Audio buffers are cleared from server RAM immediately following transcription. Classgrid does **not** maintain long-term audio recordings on disk unless specifically requested and authorized by the user for session archiving.

### 6.3 Hard Call Duration Caps
- To prevent accidental dangling voice connections or toll abuse, voice calls are programmatically terminated at **fifteen (15) minutes**.
- An automated verbal warning sounds 15 seconds prior, followed by an immutable 30-second disconnect sequence.
- Voice call volume is throttled to fifty (50) calls per 24 hours per account.

## 7. INFRASTRUCTURE & NETWORK SECURITY

### 7.1 Perimeter Defense & DDoS Protection
- **Cloudflare Edge Shielding:** The entire Platform sits behind Cloudflare's enterprise edge network, providing automatic Layer 3, Layer 4, and Layer 7 DDoS mitigation.
- **Web Application Firewall (WAF):** Real-time inspection of HTTP requests blocks SQL injection, cross-site scripting (XSS), server-side request forgery (SSRF), and known vulnerability payloads.

### 7.2 Cryptographic Standards
- **In-Transit Encryption:** All external and internal service-to-service communication requires **TLS 1.3** (or TLS 1.2 minimum) with modern, forward-secret cipher suites.
- **At-Rest Encryption:** Databases (PostgreSQL/Supabase), Redis clusters, and cloud backup snapshots are encrypted using **AES-256**. Sensitive configuration keys and external service credentials are encrypted using envelope encryption with dedicated cloud key management systems.

### 7.3 Database Security & Multi-Tenancy
- Database tables implement Row-Level Security (RLS) policies where applicable, ensuring that queries are strictly isolated to the authenticated user's scope.
- Database access is permitted only from private VPC subnets; public internet exposure of database ports is prohibited.

## 8. USAGE METERING & BILLING SECURITY

### 8.1 Atomic Credit Accounting
- Credit balances are managed via atomic transactions in high-performance Redis and relational PostgreSQL clusters.
- Token consumption updates use atomic conditional operations to eliminate race conditions, double-spending, or negative balance vulnerabilities during concurrent agent invocations.

### 8.2 Payment Gateway Signature Verification
- Top-up payments are processed through Razorpay.
- Every payment notification received via webhooks is validated using HMAC-SHA256 signature verification before compute credits are credited to an account. Unsigned or invalid webhook calls are rejected and logged as security anomalies.

## 9. VULNERABILITY MANAGEMENT & INCIDENT RESPONSE

### 9.1 Continuous Security Auditing
- Dependencies are automatically audited for known vulnerabilities (CVEs) using automated software composition analysis (SCA) tools in CI/CD pipelines.
- Security patch updates for base container images and Linux sandbox runtimes are deployed on a continuous schedule.

### 9.2 Incident Response Protocol
Classgrid maintains a dedicated Incident Response Plan structured around five stages:
1. **Detection & Triage:** Automated alerting triggers triage within 15 minutes of an anomaly.
2. **Containment:** Dynamic isolation of affected containers, sandbox clusters, or accounts.
3. **Eradication:** Neutralization of root causes and deployment of targeted code patches.
4. **Recovery:** Safe restoration of affected systems with validated data integrity.
5. **Post-Mortem & Notification:** Transparent root-cause analysis and timely notification to impacted users and regulatory authorities under the DPDP Act 2023.

## 10. RESPONSIBLE DISCLOSURE & VULNERABILITY REPORTING

We welcome security researchers and developers to inspect Our public platform responsibly. If You discover a security vulnerability in the Classgrid Platform, We ask that You report it promptly to enable remediation.

### 10.1 Ground Rules for Responsible Disclosure
- Report vulnerabilities privately to `security@classgrid.in`.
- Do **not** exploit the vulnerability to view, modify, or exfiltrate data belonging to other users.
- Do **not** execute volumetric denial-of-service (DDoS) attacks or disrupt production services.
- Give Us a reasonable period of thirty (30) days to address the issue before making any public disclosure.

### 10.2 Safe Harbor
If You conduct Your research in good faith, in compliance with these guidelines, and without harming Users or platform uptime, Classgrid will not pursue legal action against You.
